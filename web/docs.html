How it works

blog.dliu.com is a blog that anyone can read and only the owner (or an agent with the owner’s Microsoft access token) can write. There are no servers: published posts are plain files in S3, CloudFront delivers them, and one small Lambda function runs only when the owner signs in, saves a post or uploads a file.

Running costs

Everything is billed per use. With nobody writing, the only charge is storing the pictures and files in S3; reading the blog runs no code.

Security

Anyone can read published posts; only the owner, signed in with Microsoft, can write, publish or delete, and can let an AI agent write through the Microsoft API with a short-lived Microsoft access token. Draft text never leaves the database.

How the blog is checked

Every 15 minutes, status.dliu.com checks this blog the way an ordinary visitor would: it never signs in and never changes anything. It opens the public pages and links, then asks the blog’s own /health check whether the database, storage and sign-in settings it relies on are working.

What is checked

  • Pages The home page opens. If this fails, readers can’t open the blog at all.
  • Posts The list of published posts loads, and the database posts are saved in answers. If this fails, readers see no posts and the owner can’t save.
  • Published content storage The storage that holds published posts, pictures and files answers. If this fails, posts, pictures and files don’t open.
  • Reactions The reaction counts under each post load. If this fails, readers can’t see or leave reactions, but posts still read fine.
  • Blog API The small program behind the site answers. If this fails, reactions, sign-in and writing stop working.
  • Microsoft sign-in The Sign in button leads to Microsoft and the sign-in settings can be read. If this fails, the owner can’t sign in to write; readers aren’t affected.
  • Docs These documentation pages open. If this fails, only the documentation is missing.
Technical details: guest checks

Anonymous GET only: no cookies, no Authorization, no query string, redirects not followed. User agent dliu-status-bot/1.0 (+https://status.dliu.com/docs).

  • pages: GET https://blog.dliu.com/ → 200 text/html, contains dl-footer; slow after 2000 ms.
  • posts: GET https://blog.dliu.com/content/index.json → 200 application/json, JSON key posts; slow after 2000 ms.
  • reactions: GET https://blog.dliu.com/api/reactions/2026103100 → 200 application/json, JSON key counts; slow after 3000 ms. Read only; never POST.
  • api: GET https://blog.dliu.com/api/me → 200 application/json, JSON key signedIn (value false); slow after 3000 ms.
  • signin: GET https://blog.dliu.com/auth/login → 302, Location starts with https://login.microsoftonline.com/; slow after 3000 ms.
  • docs: GET https://blog.dliu.com/docs → 200 text/html, contains dl-tabs; slow after 2000 ms.
Technical details: /health

GET https://blog.dliu.com/health (or HEAD), no authentication. CloudFront forwards no cookies, no Authorization header and no query string, and caches the answer for 60 s (Cache-Control: public, max-age=60, cache key empty). /health/ redirects to /health.

Content-Type: application/health+json; HTTP 200 for pass or warn, 503 for fail. Checks run in parallel, each with a 2 s timeout; over 1 s is warn (slow); a failure is fail (timeout or read failed). The top-level status is the worst. No writes, no S3 LIST, no Microsoft calls; no names, counts or traces in the answer.

  • posts (Posts): DynamoDB GetItem of a fixed key on the posts table.
  • reactions (Reactions): DynamoDB GetItem of a fixed key on the reactions table.
  • storage (Published content storage): S3 HeadObject of content/index.json.
  • signin (Microsoft sign-in): the SSM Parameter Store read sign-in already does (cached 5 minutes); no call to Microsoft.

What isn’t tested

A guest can’t check anything that needs the owner to sign in or that changes content:

  • Signing in itself (it needs the owner’s Microsoft account), and being signed in.
  • Writing, editing, publishing, unpublishing and deleting posts.
  • Uploading pictures and files to a post, or deleting them.
  • The Microsoft API for AI agents (it needs a Microsoft access token).
  • Leaving a reaction (that is a write), and its rate limit.
  • Clearing CloudFront’s copy after the owner deletes or replaces a picture.
  • The link preview of a particular post (posts can be unpublished or deleted).
Technical details: rules
  • The tests are read only and must never change content: GET and HEAD only, never POST, PUT or DELETE.
  • No cookies, no Authorization header and no credentials of any kind.
  • At most one run every 15 minutes (plus one retry of a failed check).
